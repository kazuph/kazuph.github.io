# ARCHITECTURE.md

4 人オンライン早押しクイズを Cloudflare の機能だけでどう作ったか、その選定理由と
採らなかった案をまとめます。

## 1. 採用したアーキテクチャ

```
┌──────────────────────┐        HTTP         ┌────────────────────────────┐
│ ブラウザ（4 人）       │ ─────────────────▶ │ Worker (src/worker.ts)      │
│  public/index.html   │  POST /api/rooms    │  - /api/* をルーティング     │
│  public/app.js       │  POST .../join      │  - 部屋コード発行            │
│                      │  GET  .../ws  ─────┐│  - それ以外は Static Assets  │
└──────────────────────┘                    │└──────────────┬─────────────┘
        ▲   WebSocket(双方向)                │               │ env.QUIZ_ROOMS.get(idFromName(code))
        │                                   ▼               ▼
        │                        ┌──────────────────────────────────────────┐
        └────────────────────────│ QuizRoom Durable Object（1 部屋 = 1 DO）  │
                                 │  - WebSocket Hibernation API             │
                                 │  - ゲーム状態を DO Storage に永続化        │
                                 │  - 締切は DO Alarm で進行                 │
                                 │  - 正誤・点数・早押し順をここで決定         │
                                 └──────────────────────────────────────────┘
```

- **Worker**: 静的アセット（`public/`）の配信と `/api/*` のルーティング。
  `POST /api/rooms` で部屋コードを発行し、`idFromName(code)` で該当 DO を呼ぶ。
- **Durable Object `QuizRoom`（1 部屋につき 1 インスタンス）**: ゲーム状態の唯一の正（single source of truth）。
  WebSocket 接続、状態遷移、正誤判定、点数、早押しの受付順をすべて担当。
- **WebSocket Hibernation API（`ctx.acceptWebSocket`）**: 接続を保持しつつ DO を休止させられる。
  休止しても状態は DO Storage から復元される。
- **Durable Object Storage（SQLite バックエンド）**: 状態を書き込むので、DO の再起動や
  回線断のあとも点数・席が残る。
- **Durable Object Alarms**: 「出題 20 秒」「回答 10 秒」「正解発表 4 秒」の締切をサーバー側で進める。

### ポートとローカル実行

- `wrangler.jsonc` の `dev.port` を `8787` に固定。inspector は `0`（自動割り当て）にして
  他プロセスと衝突させない。開発サーバーを 8787 以外で常駐させない。
- 結合テスト・E2E の中だけで一時的に別ポートの `wrangler dev` を起動する（テスト終了時に停止）。
- デプロイ設定（`routes`, `account_id` など）は持たず、`wrangler dev` のローカルモードだけで動く。

## 2. なぜこの構成にしたか

| 要件 | この構成での解決 |
| --- | --- |
| 早押しの同時押しで 1 人だけ | DO は 1 部屋 1 インスタンスでメッセージを直列処理する。状態遷移（`buzz()`）は同期的に実行し、最初の 1 人で `answererId` を確定。以降の押下は棄却する。 |
| 正誤・点数をサーバーで決める | 正解番号は `src/questions.ts` にあり、判定は `src/game.ts` の純粋関数。クライアントへは `publicState()` で **reveal まで正解を送らない**。 |
| 残り時間が全員そろう | サーバーが締切（epoch ms）と `serverNow` を配信し、クライアントは差分で残り時間を描画。クライアント時計を信用しない。 |
| 20 秒・10 秒の締切 | DO Alarm でサーバー側が `tick()`。誰も押さなくても 20 秒で正解発表、4 秒後に次の問題へ自動で進む。 |
| 再読み込み・切断からの復帰 | `playerId + token` を localStorage に保存。再接続時に DO が Storage 上のトークンと照合し、点数・席をそのまま返す。WebSocket は 800ms 間隔で自動再接続。 |
| リアルタイム双方向 | WebSocket で全員へ公開状態をブロードキャスト。 |
| 外部サービスなし | 使用するのは Workers / Durable Objects / WebSocket / DO Storage / DO Alarms のみ。 |

### 状態遷移

```
lobby ──start（2〜4人, ホスト）──▶ buzzing ──buzz（最初の1人）──▶ answering
  ▲                                  ▲                              │
  │                                  │ 不正解（-5, その人はもう押せない） │ 正解（+10）
  │                                  └──────────────────────────────┘
  │                                                                 │
  │                                                     reveal ◀────┘
  │                                                       │ 4 秒
  │reset（ホスト）                        buzzing（次の問題）│
  └──────────────── finished ◀── 10 問終了 ────────────────┘
```

- `buzzing` で 20 秒経過 → `reveal`（正解者なし）
- `answering` で 10 秒経過 → 回答権を手放して `buzzing` に戻す（減点なし）
- 全員が不正解（`buzzedOut`）になったら即 `reveal`

## 3. サーバー権威の徹底

- クライアントから受け取るのは `start` / `buzz` / `answer` / `leave` / `reset` / `ping` の意図だけ。
  点数や正誤、誰が回答権を持つかをクライアントが申告する経路は無い。
- 配信する `PublicState` には **トークンを含めず**、正解番号も `reveal` のときだけ含める
  （単体テストで「出題中は `answerIndex` を含まない」ことを検証）。
- 部屋コードは紛らわしい文字を除いた 4 文字。`idFromName(code)` で衝突を検出し、衝突時は引き直す。

## 4. 却下した代替案

| 案 | 却下理由 |
| --- | --- |
| **Workers + KV** | KV は結果整合で read-modify-write の原子性が無く、同時早押しの勝者を 1 人に確定できない。サーバーからの push もできず TTL 制約もある。 |
| **Workers + D1** | 早押しの競合を DB のトランザクションで解決するのは複雑でレイテンシも大きい。リアルタイム push の仕組みが別途必要になる。 |
| **Workers のみ（状態はクライアント）** | 正誤・点数をブラウザが申告することになり「サーバーで決める」という決定事項に反する。 |
| **全部屋を 1 つの Durable Object に集約** | 1 インスタンスに負荷と障害が集中する。1 部屋 = 1 DO なら部屋単位で分離・スケールでき、障害も局所化できる。 |
| **SSE + POST** | サーバー→クライアントは可能だが、双方向・低遅延の早押しには WebSocket が素直。Hibernation も WebSocket 前提。 |
| **外部リアルタイムサービス（Ably / Pusher / Supabase Realtime 等）** | 有料・外部依存であり、決定済み事項で禁止。 |
| **Cloudflare Queues / Workflows でタイマー処理** | 秒単位の締切には大げさで、DO Alarm で十分かつ部屋ごとに閉じる。 |
| **D1 に問題バンクを持ち外部から取得** | 「問題はアプリに内蔵（外部 API から取らない）」という要件に反する。 |

## 5. 再接続の設計（要件 10 の要）

1. 作成/参加時に Worker が `playerId` と秘密の `token` を発行して返す。
2. クライアントは localStorage に保存し、以降の WebSocket 接続に付ける。
3. DO は `tokens[playerId] === token` を検証。一致すれば**満員でもゲーム中でも**接続を許可する。
4. 切断してもプレイヤーは削除せず `connected=false` にするだけなので、点数と席が残る。
5. 同じプレイヤーが新しい接続を張ったら古いソケットは閉じ、`connected=true` に戻して
   最新の公開状態を送る。
6. WebSocket Hibernation により DO が休止しても、Storage から状態を復元して継続する。

## 6. テスト戦略

| 層 | ツール | 何を確かめるか |
| --- | --- | --- |
| 単体 | vitest (Node) | `src/game.ts` の純粋ロジック。定員、開始条件、同時押しの勝者 1 人、正誤と点数、締切、全員不正解、10 問終了、順位、公開状態に答えが漏れないこと。 |
| 結合 | vitest + 本物の `wrangler dev`（テスト内だけ別ポート） | 実際の Workers ランタイム + Durable Object + WebSocket に 4 クライアント同時接続。同時押し、5 人目拒否、ホスト限定開始、再読み込み復帰、20 秒 alarm と自動遷移。 |
| E2E | Playwright (Chromium) | PC 幅 / スマホ幅で 4 人がフルゲームを最後まで遊ぶ、5 人目の理由表示、ゲーム中の再読み込み復帰。各画面のスクリーンショット取得。 |

単体テストはゲームルールの網羅、結合テストは「サーバー権威・同時実行・永続化・タイマー」、
E2E は「実際に人が遊べること・レスポンシブ」を担い、役割を分けています。

## 7. 既知の制限・今後

- 切断したプレイヤーは自動では退去させず席を保持する（復帰優先）。長期放置の部屋は
  DO Storage に残り続けるため、実運用では TTL や掃除が必要。
- 1 部屋につき回答権は常に 1 人。切断者を考慮した「席の解放」は未実装。
- 問題は固定順（ランダム化なし）。テストを決定的にするための選択。
- 水平スケールは部屋単位（1 DO = 1 部屋）。同一部屋の負荷は最大 4 人なので問題にならない。
- デプロイは想定外（ローカル専用）。
