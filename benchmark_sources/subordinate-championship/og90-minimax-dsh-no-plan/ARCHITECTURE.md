# ARCHITECTURE — 早押しクイズ（Cloudflare Workers / Durable Objects）

## 1. 結論（採用した構成）

```
ブラウザ（4人）
   │  WebSocket（/api/rooms/:code/ws）
   ▼
Cloudflare Worker（src/worker.ts）
   │  ・部屋コードの発行（POST /api/rooms）
   │  ・/api/rooms/:code/ws を Durable Object へ振り分け
   │  ・それ以外は Workers Assets（public/）を配信
   ▼
Durable Object（src/room.ts）＝ 1 部屋 = 1 DO
   │  ・WebSocket Hibernation API で参加者を保持
   │  ・DO Storage に部屋状態を保存（再接続・再起動に対応）
   │  ・DO Alarms で 20 秒 / 10 秒 / 2.5 秒 / 1.5 秒の自動進行
   ▼
Durable Object Storage（SQLite / ローカル開発では .wrangler/state）
```

採用した Cloudflare の機能と、その理由です。

| 機能 | 使いどころ | 選んだ理由 |
| --- | --- | --- |
| **Workers** | HTTP ルーティングと静的配信 | アプリの入口。ローカル開発 (`wrangler dev`) と本番のランタイムが同じなので、挙動が一致する |
| **Durable Objects** | 1 部屋 = 1 DO | 「早押しを同時に押されたときに 1 人だけを選ぶ」ため、**1 部屋に 1 つの逐次実行単位**が必要だった。DO は 1 インスタンスにつき 1 isolate でイベントを逐次処理するため、先着順が自然に保証される |
| **WebSocket（Hibernation API）** | プレイヤー ↔ サーバー | 常時接続の双方向通信。Hibernation API を使うと DO がメモリから退避しても接続と添付情報が保たれるため、再接続が軽い |
| **DO Storage** | 部屋状態の永続化 | プレイヤー・得点・出題位置を保存するので、DO の再起動やブラウザの再読み込みでも同じ状態から再開できる |
| **DO Alarms** | 時間の自動進行 | `setTimeout` は DO が退避すると失われるため、確実なタイマーとして Alarms を使う。締切は状態にも保存し、遅延しても画面が破綻しない |
| **Workers Assets** | `public/` の配信 | ビルド不要の素の HTML/CSS/JS をそのまま配信。デプロイしない前提でも動かしやすい |

### 部屋コード = Durable Object の ID

部屋コード（6 文字）をそのまま `env.ROOM.idFromName(code)` に渡しています。
これにより **「コード → どの部屋か」の解決表（KV や D1）が不要** になり、
部屋の新規作成・照会は Worker 内の 1 回の `stub.fetch` で完結します。
コードの衝突は Worker 側で 8 回まで再生成して回避します。

## 2. サーバーが権威を持つ設計

早押しクイズでは「誰が先に押したか」をミリ秒単位で決めないといけません。
そのため、判定はすべてサーバー側で行い、ブラウザは「状態を描くだけ」にしています。

| 判断 | 担当 | 実装 |
| --- | --- | --- |
| 早押しの順番 | Durable Object | `buzz()`（`src/game.ts`）。DO のイベントは逐次処理されるため、**最初に受信した人が回答権**を得る |
| 回答権の期限 | Durable Object | 回答権取得 +10 秒（`ANSWER_MS`）。期限切れは不正解として -5 点 |
| 正誤判定 | Durable Object | `answer()`。ブラウザが送るのは選択肢の index だけ。正解 index は `src/questions.ts`（サーバー側）にしか無い |
| 得点 | Durable Object | 正解 +10 / 不正解 -5。クライアントは `state.players[].score` を表示するだけ |
| 残り時間 | Durable Object | 締切の絶対時刻（サーバー時刻）を配信し、クライアントは `serverNow` との差で補正して表示 |

ブラウザから送られるメッセージは 5 種類だけです（`src/types.ts` の `ClientMessage`）。

```ts
{ t: 'join', id, name }   // 入室 / 再接続
{ t: 'start' }            // 開始（ホストのみ）
{ t: 'buzz' }             // 早押し
{ t: 'answer', choice }   // 選択肢を選ぶ（index のみ）
{ t: 'restart' }          // ホストがスコアをリセットしてやり直す
```

## 3. 状態機械（`src/game.ts`）

```
lobby ──start(ホスト, 2〜4人)──▶ question ──正解──▶ reveal ──2.5秒──▶ question(次の問)
                                   │  ▲                                    
                                   │  └────── 次の人有給 / 早押し再開 ◀─┐ 
                                   │                                       │
                                   ├──不正解──▶ feedback ──1.5秒──────────┘
                                   ├──10秒時間切れ──▶ feedback（-5点）
                                   ├──20秒経過 or 全員回答──▶ reveal
                                   └──(10問完了)──▶ result
```

- 問題文・選択肢・解説は `src/questions.ts` に内蔵した 10 問（外部 API は一切使わない）
- `tick(state, now)` が経過時間に応じた自動進行をすべて行う（`src/game.ts`）
  - 同じ関数を **WebSocket メッセージの受信時**と **Alarm の発火時**の両方で呼ぶため、
    アラームが遅延しても状態の矛盾は起きない

## 4. 同期の仕組み

- 状態が変わると Durable Object が **全員に最新の state を配信**する（`broadcast()`）。
  接続している全員に同じ画面が流れるので、「点数が違う」「残り時間が違う」等问题が起きない。
- クライアントは `state` メッセージを受けるたびに UI を描き直す（`public/app.js` の `render()`）。
  残り時間だけは `requestAnimationFrame` のループで減少させて滑らかに動かす。
- 切断中のプレイヤーは一覧に残る（点数を保持したまま「切断中」タグを表示）。

## 5. 再接続の設計

- 参加時にクライアントが `crypto.randomUUID()` で **プレイヤーID（トークン）** を発行し、
  `localStorage` に保存する（キーは部屋コード単位）。
- 再接続時は同じトークンを `join` メッセージで送る。DO は既知のトークンなら
  そのまま「そのプレイヤーの復帰」として扱い、**得点は一切リセットしない**。
- 同じトークンで二重接続した場合、古いソケットを DO 側で閉じて 1 接続に収束させる。
- 切断したプレイヤーは「切断中」になるが、席と点数は保持される（復帰のために席を空けない）。
- クライアントは切断時に 0.4 秒 → 4 秒までのバックオフで自動再接続する。

## 6. 選ばなかった案

| 案 | 不採用の理由 |
| --- | --- |
| **素の Worker + メモリ上の部屋状態（Map）** | Worker インスタンスは複数・再起動するため、1 部屋に 1 つの順序保証 корабがない。同時押しで先着順を決められない。またインスタンスが別になると全员の画面が割れる |
| **Workers + WebSocket + D1（状態を DB に置く）** | D1 は同期 API ではないため「最初の 1 -request だけを回答権にする」という原子的な先着処理が難しい。DO なら同じ isolate 内の逐次処理で自然に満たせる |
| **Workers + KV** | KV はEventually Consistent で、条件付き更新（compare-and-swap）ができない。早押しの先着判定には使えない |
| **Cloudflare Realtime / PubSub・Durable Objects のブロードキャスト全体** | 部屋ごとの独立したゲーム状態（得点・出題位置・回答権）を持つため、部屋単位に分離する設計ではなく、DO の方が自然。另外、有料サービスや外部PubSubは使わない方針 |
| ** Workers + D1 + ポーリング** | 20 秒・10 秒の締切がある早押しには 1 秒単位のポーリングは精度・負荷とも NG。WebSocket の方が適している |
| **クライアント側で正誤判定（サーバーは点数を保存するだけ）** | 「サーバーが最初に受け取った 1 人だけ」の保証が壊れる。クライアントの時計や申告を信頼することになり、課題の条件（ブラウザの申告を信用しない）に反する |
| **Vite プラグイン / フロントエンドフレームワーク** | 画面は 5 画面しかないため、素の HTML/CSS/JS で十分。ビルド不要にして起動を速くした |

## 7. 信頼性・既知の制約

- **書き込みの直列化**: DO のイベント（WebSocket メッセージ / Alarm / fetch）は同時に走れるため、
  ストレージ書き込みは `writeChain` で直列化している。ローカル開発では複数の部屋が
  同じ SQLite ファイルを共有するため `SQLITE_BUSY` がまれに出るが、軽くリトライする。
- **タイマーの精度**: Alarms は秒単位の精度なので、実際の切り替えは数十〜数百 ms 遅れることがある。
  締切はサーバーに保存してあり、表示は `serverNow` で補正している。
- **10 秒の回答時間切れ**: -5 点として扱う（不正解と同じ）。仕様書に「時間切れ」の扱いは
  記載がないため、本アプリでは不正解に準じた。
- **同時ログインの扱い**: 同じトークンで 2 台同時に開くと、古い接続が切断される（新しい方だけが残る）。
- **ローカル開発限定**: アカウントへのログインやデプロイは行わない。`wrangler dev` の
  ローカルモードだけで完結する構成にしている。

## 8. ファイル責務

| ファイル | 責務 |
| --- | --- |
| `src/worker.ts` | HTTP ルーティング、部屋コード発行、DO への振り分け、Assets 配信 |
| `src/room.ts` | Durable Object。WebSocket の受け入れ、メッセージ処理、状態の保存、Alarm による自動進行、状態配信 |
| `src/game.ts` | 純粋なゲームロジック（参加・開始・早押し・回答・自動進行・順位）。I/O を持たないので単体テストが容易 |
| `src/questions.ts` | 内蔵の問題バンク 10 問 |
| `src/types.ts` | クライアントとサーバーが共有する型定義 |
| `public/app.js` | 状態を描くだけのクライアント。DOM の更新と再接続のみを担当 |
