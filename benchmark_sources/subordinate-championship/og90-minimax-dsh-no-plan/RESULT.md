## 2. テストについて

### 2.1 テストの層構成

| 層 | ファイル | 目的 | 件数 |
| --- | --- | --- | --- |
| 単体（Node） | `test/unit/game.test.ts` | ゲームロジック（参加・開始・早押し・回答・自動進行・順位・問題バンク）の純粋関数を検証 | 25 |
| 結合（Node + 実サーバー） | `test/integration/ws.test.ts` | `wrangler dev` を 8799 番で一時起動し、実 WebSocket でプロトコルを検証 | 8 |
| 結合（実 Workers ランタイム） | `test/workers/room.test.ts` | Durable Object の HTTP API・状態保存・メッセージハンドラ・アラーム | 6 |
| E2E（Chromium） | `test/e2e/quiz.spec.ts` | ブラウザで 4 人同時参加・同時早押し・再読み込み復帰・最終順位（PC 幅 / スマホ幅） | 7 × 2 |
| E2E（スクリーンショット） | `test/e2e/screenshots.spec.ts` | ロビー・出題中・回答中・結果の画面を PC / スマホ幅で保存 | 1 × 2 |

合計 **39 テスト（Node）+ 16 テスト（ブラウザ）** がすべて成功しています。

### 2.2 課題で要求された 3 点の明確化

| 要求 | 実装 |
| --- | --- |
| 同時押しで 1 人だけが回答権を得る | E2E（2 ブラウザが同時にクリック → 回答権表示がちょうど 1 つ）と結合テスト（4 クライアントが同時送信 → 回答権 1 人 + 順番待ち 3 人）の両方で検証。サーバー側で先着順を決めるため、2 人目の早押しは「順番待ち」になる |
| 再読み込みで復帰できる | E2E で 10 点獲得 → `page.reload()` → 同じ名前・同じ点数でゲーム画面に戻ること、対戦者からも同じ点数に見えることを確認。実装は `localStorage` のプレイヤー ID（UUID）で Durable Object 上のプレイヤーを同定する方式 |
| 4 人が同時に遊べる | E2E で 4 つの独立したブラウザコンテキストが 1 つの部屋コードに参加し、全員で参加者 4 名・同じ画面・同じ得点 Seeing ことを確認 |

### 2.3 テストで分かったこと・改良点

- Durable Object のイベントは 동시에走れるため、ストレージ書き込みを直列化しないと
  ローカル開発で `SQLITE_BUSY` が発生した（`src/room.ts` の `writeChain` + リトライで対処）。
- 画面側では「早押し」ボタンにイベントリスナーが抜けていたのを E2E で検出し、修正した。

## 5. 未達・代用・制約（正直な記録）

| 項目 | 状況 |
| --- | --- |
| 回答権の 10 秒タイムアウト | 仕様書に「10 秒以内に選ぶ」とあるため、時間切れは **不正解と同じ -5 点**として実装しました（仕様書には時間切れの点数の指定がない）。自動テスト（単体）で検証済み |
| クライアントの自動再接続（バックオフ） | 実装済み（0.4 秒 → 4 秒で再接続）。ただし「回線を切断してから自動で戻る」ことをブラウザ操作で再現する自動テストは未作成。再接続後の**同一プレイヤーとしての復帰**は結合テストと E2E で検証済み |
| 4 人が 1 台の PC で遊ぶ場合 | 1 ブラウザでは 1 プレイヤーとして扱われます。4 人を 1 台で遊ぶには Cookie 領域を分けたウィンドウ（または別のブラウザ）が必要です（README に記載） |
| タイマーの精度 | Durable Object Alarms は秒単位のため、実際の切り替えは数十〜数百 ms 遅れることがあります。締切はサーバーに保存し `serverNow` で補正して表示しています |
| 本番デプロイ | 課題の方針どおり未実施（デプロイしない構成） |
| 画像生成 | 課題の条件どおり画像生成ツールは使用せず、UI は CSS のみで作っています |
