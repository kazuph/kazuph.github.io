# QUICKの構成と判定の設計

## 選んだ構成

Workersが静的ファイルとHTTP入口を担当し、部屋コードを名前にしたDurable Objectへルーティングする。1部屋1オブジェクトが参加者、問題、得点、回答権、期限を所有する。全員のWebSocketをこのオブジェクトへ接続するため、受信順の単一の判定場所ができる。SQLiteには部屋のJSONスナップショットを保存し、WebSocket Hibernation APIで接続を扱う。

```text
PC / スマホの4ブラウザ
       │ HTTP: 作成・参加 / WebSocket: 開始・早押し・回答
       ▼
Workers ─── Static Assets（HTML / CSS / JS）
       │ 部屋コードから同じオブジェクトへ
       ▼
QuizRoom Durable Object（1部屋ごと）
       ├── 同期した状態遷移 → SQLite保存
       ├── 全員へ同じ状態をWebSocket配信
       └── Alarm → 回答期限 / 問題期限 / 次の問題
```

### 採用しなかった案

| 案 | 採用しない理由 |
| --- | --- |
| Workers + KV | 複数の早押しの排他決定に使わず、部屋の直列処理をDOへまとめる方が明確 |
| Workers + D1 + ポーリング | 排他更新と配信と期限の仕組みが別々になり、この4人対戦には構成が増える |
| ブラウザ側で先着や点数を申告 | 改ざんや端末時計の差で勝敗が変わるため不適合 |
| 外部のリアルタイムサービス | 決定済みのCloudflare内完結・外部有料サービス不使用に反する |

## 状態と不変条件

`lobby → question → answering → reveal → question` を10問繰り返し、最後に `results`。
誤答・回答時間切れなら `answering → question` に戻し、回答者をその問題の失権リストに追加する。全員が失権したら公開する。

- 定員4人。開始はホストだけで2〜4人。開始後の新規参加は拒否する。
- `question`だけで早押しを受理し、受信イベント内で同期的に`answering`へ変える。他のイベントとの間に`await`を置かない。SQLite保存まで同期なので、4件の競合で権利が複数に分かれない。
- すべての早押し・回答に問題番号が必要。前問で遅れた操作が次問に流れ込むことを拒否する。
- サーバーは接続に紐づく本人からしか回答を受理せず、回答権と選択肢範囲を確認。送られた点数やプレイヤーIDを信用しない。
- 正解・資格情報は公開前の状態配信から除外する。点数の変更は内蔵問題の正解番号でのみ決める。
- 状態を保存してから配信する。部屋の復元はSQLite、接続の本人情報はWebSocket attachmentから得る。

## 期限

出題時に20秒の絶対期限をサーバー時刻で設定。早押しを受理すると10秒の回答期限を設定するが、問題全体の20秒を超えない。すべての操作の前にも期限を確認するため、Alarmの発火が遅れても期限後の回答や押下を受理しない。`now >= deadline`で締め切る。

Alarmは現在の最も近い期限を予約する。正解、全員失権、20秒で正解公開。表示のための3秒（`REVEAL_MS`）後、サーバーが自動で次問または結果へ進める。これは回答を受け付けない表示期間で、TASKの10秒/20秒の判定には足さない。問題出題後の期限は毎問新しく設定する。Alarm再配送は現在の状態と期限を再確認する。

無回答は不正解を選んでいないため無得点として失権する。この解釈、正解時の即公開、同点の競技順位方式はTASKに詳細がなかったためREADMEにも明記した。正解時に他プレイヤーは追加で回答できない。

残り秒数は配信のサーバー時刻と絶対期限から計算する。画面描画を100ms間隔で更新し、端末の時計の差を配信時に補正。ネットワーク遅延や描画タイミングで秒の境界には差が生じるため、E2Eでは4画面の残り時間の最大差1秒と、回答者・得点の一致を検査する。判定にブラウザの残り秒数は使わない。

## 参加・復帰の契約

| 経路 | 契約 |
| --- | --- |
| `POST /api/rooms` | `{name}`で作成、201 `{code,id}`、参加Cookieを発行 |
| `POST /api/rooms/:code/join` | `{name}`で参加、201 `{code,id}`。満室/対戦中409、不在404 |
| `GET /api/rooms/:code/socket` | Cookie認証後WebSocketへ昇格。未認証401 |
| WS `start` | 接続本人がホストかつ2〜4人なら開始 |
| WS `buzz` | `{type:'buzz',question}`。先着かつ未失権なら回答権 |
| WS `answer` | `{type:'answer',question,choice}`。権利者の0〜3のみ |
| WS `state` | `{type:'state',state,you}`。revision、期限、全員の得点と接続状況、出題、公開中だけ正解 |
| WS `error` | `{type:'error',error}`。拒否理由を画面へ表示 |

Cookieは暗号学的乱数で発行する参加トークン。HttpOnly・SameSite=Strict・部屋単位のPath。WebSocket URLに資格情報を載せない。リクエストのOriginがあれば同一Originであることを確認する。ユーザー名はHTMLとして挿入せずエスケープする。

URLのhashに部屋コードを残し、再読み込み時には同じCookieで接続する。切断でも席を消さない。新しい同一プレイヤーの接続は旧接続を閉じて二重操作を抑える。一時オフラインでは接続を閉じ、オンラインイベントと再接続で最新状態を取得する。Cookie喪失時に名前だけで得点を引き継ぐことは許可しない。

## ローカル運用と検証

`wrangler dev --local --port 8784 --inspector-port 0`。ローカルDOとSQLiteを使い、アカウントもクラウドリソース作成も不要。buildは`wrangler deploy --dry-run`でバンドルだけを出力する。永続データは`.wrangler/state/`、証拠は`.artifacts/`。

状態機械の24順列・境界テスト、実HTTPと実WebSocketの権限/定員/先着テスト、4独立ブラウザの通常UIでの完走テストを併用する。偽時計・モック・テスト専用短縮期限・認証迂回はない。UIの8画像に加え、横はみ出し・操作領域と参加者行の重なりを矩形の交差で検査する。

参考：[Cloudflare WebSocket Hibernation API](https://developers.cloudflare.com/durable-objects/best-practices/websockets/)、[Alarm API](https://developers.cloudflare.com/durable-objects/api/alarms/)。互換日は固定版Wranglerの対応日を使用し、closeフレームへの自動返信が有効。1005など送信禁止コードをcloseで返さない。

## 検証の限界

課題はローカルのみ。異なる物理端末・実インターネットの遅延やクラウド配備は未検証。サーバープロセス停止をまたぐ復元の故障注入は別途検証が必要。席の解放・ホスト移譲・無期限保存データの清掃は実装していない。ローカル用途の範囲を超える運用機能は追加していない。
