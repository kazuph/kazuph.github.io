# アーキテクチャ

## 結論

Cloudflare Workers の上に、次の組み合わせだけで作りました。

| 要素 | 使い方 | 選んだ理由 |
|---|---|---|
| Workers | `/api/*` の受付、部屋コードの発行、静的ファイルの配信 | 実行環境が Cloudflare Workers という決定事項にそのまま合う。追加のサーバーを持たない |
| Durable Objects（SQLite 版） | 1部屋 = 1オブジェクト。状態の保存と全メッセージの直列処理 | 1部屋の状態を1か所に閉じ込められ、同時押しの順番を単一スレッドで決められる。SQLite ストレージに状態を永続化できる |
| WebSocket（Hibernation API） | ブラウザと部屋の双方向通信 | 出題・早押し・回答・締め切りを低遅延で全員に配信できる。Hibernation でアイドル時のコストを抑えられる |
| Alarm | 20秒・10秒・3秒の締め切りと、接続の死活監視 | 誰もメッセージを送らなくてもサーバー側で時間を進められる。クライアントの時計を信用しない |
| Workers Static Assets | `public/` の HTML / CSS / JS を配信 | フロントのビルド工程をなくし、依存を減らす。`run_worker_first` で `/api/*` だけ Worker に通す |
| 内蔵の問題データ | `src/questions.ts` の16問から毎回10問 | 外部APIを使わないという決定事項を守る |

外部のリアルタイム配信サービス、有料サービス、Cloudflare アカウントを必要とする機能は使っていません。

## なぜ Durable Object なのか

このゲームで絶対に壊してはいけないのは「4人がほぼ同時に押したとき、サーバーが最初に受け取った1人だけが回答権を得る」ことです。

Durable Object は部屋ごとに1インスタンスで、メッセージが直列に処理されます。4人分の `buzz` が同時に届いても、Durable Object が処理した順番がそのまま勝敗になります。ロックや分散トランザクションを自分で書く必要がありません。

また、部屋の状態（プレイヤー、点数、問題番号、締め切り、回答者）を1つの SQLite ストレージに保存できるため、Worker の別インスタンスにリクエストが行っても同じ状態を参照できます。

```
ブラウザ4台
  │  WebSocket（token）
  ▼
Worker（/api/*）
  │  idFromName(部屋コード)
  ▼
Durable Object「1部屋」
  ├─ SQLite storage: RoomState（players / scores / phase / deadlines / tokens）
  ├─ WebSocket Hibernation: 接続中の全員へ state を配信
  └─ Alarm: 次の締め切り1つを予約
```

## 状態と規則

フェーズは次の順で進みます。

```
lobby ──start──▶ question ⇄ answering ──▶ reveal ──▶ 次の question
                                                  └─ 10問後 ──▶ finished
```

- `lobby`: 参加受付。定員4人。開始はホストだけ、参加者2〜4人。
- `question`: 出題から20秒。まだ失格していない人が早押しできる。
- `answering`: 最初に `buzz` を処理された1人だけ。締め切りは「押した時刻 + 10秒」と「問題の20秒締め切り」の早いほう。
- 正解: +10点で `reveal`。
- 不正解・回答時間切れ: -5点、その問題は失格。残りがいれば `question` に戻る（問題の20秒は延びない）。
- 全員失格、または20秒経過: `reveal`。正解を全員に公開。
- `reveal`: 3秒。その後、次の問題へ。10問目なら `finished`。
- 点数はマイナス可。同点は同順位（1, 2, 2, 4）。

すべての判定は `src/game.ts` の純粋関数で、時刻 `now` を引数で受け取ります。Durable Object はメッセージを受けるたびに、まず `tick(state, now)` で期限切れの処理をまとめて進めてから入力を処理します。

## 通信

### HTTP

| メソッド | パス | 内容 |
|---|---|---|
| `GET` | `/api/health` | 起動確認 |
| `POST` | `/api/rooms` | `{ name }` → `{ code, playerId, token }` |
| `POST` | `/api/rooms/:code/join` | `{ name }` → `{ code, playerId, token }`。満員・開始後・部屋なしはエラー |
| `GET` | `/api/rooms/:code/ws?token=...` | WebSocket へ切り替え。token 不一致は 403 |

部屋コードは紛らわしい `0/O/1/I` を除いた英大文字と数字の6文字です。

### WebSocket

ブラウザ → サーバー:

```json
{ "t": "start" }
{ "t": "buzz", "q": 1 }
{ "t": "answer", "q": 1, "choice": 0 }
{ "t": "ping" }
```

サーバー → ブラウザ:

```json
{ "t": "state", "you": "...", "serverNow": 1234567890, "...": "..." }
{ "t": "error", "message": "..." }
```

状態は毎回全量を送ります。含めるのは、部屋コード、フェーズ、プレイヤー（名前・点数・接続状態・失格・ホスト・回答中）、問題文と4択、締め切り時刻、直前の回答結果、`finished` のときの順位です。

次は**送りません**。

- 各プレイヤーの token
- `question` / `answering` 中の正解番号
- 未来の問題

正解番号は `reveal` のときだけ `correctIndex` として送ります。単体テストで、出題中・回答中の公開状態に `correctIndex` が存在しないこと、token が含まれないことを確認しています。

## 再接続

- 参加時に受け取った `{ code, playerId, token }` を `localStorage` に保存します。
- ページを開いたとき保存があれば、自動で WebSocket に接続します。ロビー・ゲーム・結果のどこでも、サーバーの状態をそのまま復元します。
- 接続が切れたら1秒ごとに再接続し、画面上部に「再接続中…」を出します。
- `offline` イベントで接続を閉じ、`online` イベントで即座につなぎ直します。
- 同じ token の新しい接続が来たら、Durable Object が古い接続を閉じます。
- 切断中の席と点数は残します。ほかの人の画面には「接続が切れています」と表示します。
- 2秒ごとの `ping` と、7秒間返事がない接続を切る Alarm を併用し、TCP が切れたまま close が届かない場合にも備えます。

## 時刻

判定はすべて Durable Object の `Date.now()` で行います。クライアントには `serverNow` を送り、ブラウザは「サーバー時刻 − 端末時刻」の差だけを使って残り時間を表示します。端末の時計がずれても、全員が同じ残り時間を見られます。

Alarm は常に「いちばん近い締め切り」1つだけを予約します。メッセージ処理でも Alarm でも、`tick` のあとに次の Alarm を設定し直します。

## 採用しなかった案

| 案 | 採用しなかった理由 |
|---|---|
| Worker のメモリだけで部屋を持つ | Worker インスタンスは複数存在し得て、状態が共有されない。同時押しの順番も保証できない |
| KV に部屋状態を保存 | 結果整合性で、同時押しの勝敗がぶれる。読み書きの競合を防げない |
| D1 に部屋状態を保存 | 同時押しの直列化にはトランザクションとロックの設計が必要。Durable Object のほうが部屋単位の直列処理に向く |
| D1 / KV + ポーリング | 早押しの順番と残り時間の同期に余計な遅延が出る。WebSocket のほうが自然 |
| 外部のリアルタイム配信サービス（Firebase、Pusher など） | 有料・外部サービスを使わないという決定事項に反する |
| Cloudflare Queues / Workflows | 20秒・10秒の短い締め切りには過剰。Alarm 1つで足りる |
| React / Vue などのフロントフレームワーク | 画面数が4つで状態も小さい。ビルドなしの素の JS のほうが依存が少なく、ローカル起動が単純 |
| Cloudflare Pages + Functions | Workers + Static Assets で同じことをより少ない設定で実現できる |

## テスト方針

- **単体（vitest）**: ゲーム規則を時刻付きの純粋関数として直接叩く。4人の押す順番24通り、正解/不正解/時間切れ、20秒と10秒の締め切り、全員失格、10問終了、同順位、公開状態の情報漏れ。
- **ブラウザ（Playwright）**: `wrangler dev` を自動起動し、独立した4つのブラウザコンテキストで実際に遊ぶ。同時押し、再読み込み、回線断、実時間の20秒/10秒、残り時間の一致、最終順位、スマホ幅の収まり、スクリーンショット。
- **時間を縮めない**: 締め切りのテストは実時間で待つ。テスト用の時計操作やサーバー側の短縮フラグは入れていない。
