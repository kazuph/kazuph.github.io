# ARCHITECTURE.md

4人オンライン早押しクイズのアーキテクチャと、その選択理由・選ばなかった案をまとめます。

## 0. 結論（採用した構成）

```
ブラウザ (index.html + app.js)
  │  ① HTTP: 部屋を作る / 参加する        →  Workers Assets から配信される Worker
  │  ② WebSocket: ゲーム本体（双方向）
  ▼
Cloudflare Worker (src/index.ts)
  │  ・/api/* をルーティングし、部屋コードごとの Durable Object に委譲
  │  ・静的ファイルは Workers Assets (binding: ASSETS) から配信
  ▼
Durable Object "RoomDO" (src/room-do.ts)   ← 1部屋 = 1インスタンス
  │  ・ゲーム状態の唯一の権威（src/game-logic.ts の状態機械を回す）
  │  ・WebSocket Hibernation API で最大4本の接続を保持し、状態変化を全員へ配信
  │  ・20秒 / 10秒の締切は Durable Object Alarms で処理
  │  ・状態は Durable Object Storage に保存（再起動・ハイバネーションから復帰）
  ▼
Cloudflare のローカル実行環境（wrangler dev / workerd）
```

- 実行環境: Cloudflare Workers ランタイム（ローカルは `wrangler dev`）。デプロイ・アカウントログインは不要。
- 外部の有料サービス・リアルタイム配信サービスは一切使っていません（HTTP は同一オリジンのみ）。
- 正誤判定・点数・早押しの順番は **すべて Durable Object の中で決まります**。ブラウザから送れるのは
  「押した」「この選択肢を選んだ」という意思表示だけで、点数や順番を指定する項目はプロトコルに存在しません。

## 1. 要件から導いた設計上の制約

| 要件 | 設計上の要請 |
| --- | --- |
| 5. 最初に受け取った1人だけが回答権を得る | サーバー側で「到着順」が定義できること。複数インスタンスに分散してはならない |
| 6-8. 10秒 / 20秒の締切、不正解者の再開 | サーバー側のタイマー。クライアントの時計や申告を信用しない |
| 10. 再読み込み・切断からの復帰 | 接続と独立した永続的なプレイヤー状態（点数・席順・トークン） |
| 11. 全員の画面がそろう | 状態変化のたびに全員へ同じスナップショットを押し出す（ポーリングではない） |
| 2-3. 定員4人・開始条件 | 部屋単位の排他制御（同時参加の競合を防ぐ） |

## 2. 採用した各技術と理由

### 2.1 Durable Objects（1部屋 = 1インスタンス）

- **単一スレッド・単一権威**なので、「同時に押した」ときの順序が入力キュー順で一意に決まります。
  複数の Worker インスタンスにリクエストが分散する構成では、到着順の全順序を保証できません。
- 部屋ごとに独立しているため、部屋同士は干渉しません（状態も接続も分離）。
- 部屋コード `ABCD` をそのまま `idFromName(code)` に使い、Worker 側は状態を持ちません（ステートレス）。

### 2.2 WebSocket Hibernation API（`ctx.acceptWebSocket`）

- 早押しは「押した瞬間」を全員に伝える必要があり、双方向プッシュが必須です。
- Hibernation API では、接続が無通信のあいだ Durable Object を休ませられます（切断せずに）。
  締切は Alarm で起きるので、休んでいても正しく進行します。
- メッセージごとにプレイヤーを識別する必要があるため、`ws.serializeAttachment({playerId})` に
  接続時点でトークン認証済みの `playerId` を紐付けています。メッセージ本文の `playerId` は信用しません。

### 2.3 Durable Object Alarms（20秒 / 10秒）

- 「問題が出てから20秒」「回答権を得てから10秒」はサーバー側の締切です。
- 締切は `storage.setAlarm()` でスケジュールし、発火時にフェーズを進めます。
- クライアントは残り時間を **自分では決めません**。サーバーが各スナップショットに `now` と締切時刻を
  含めて送り、クライアントは `now` との差分（＝時計のずれ）を補正してカウントダウンを描画するだけです。

### 2.4 Durable Object Storage（SQLite-backed）

- 部屋の状態（フェーズ・点数・席・締切・回答ログ）を丸ごと保存します。
- ハイバネーション復帰やプロセス再起動のあとも、同じ部屋・同じ点数で続きから再開できます。
- 保存はゲームイベントごと（1問あたり数回）。トラフィック・コストはローカル開発では問題になりません。

### 2.5 Workers Assets（静的ファイル）

- `public/` を Workers の `assets` バインディングで配信します。`/api/*` だけ Worker が処理します。
- 別の静的サーバーを立てる必要がなく、同一オリジンなので WebSocket も CORS も簡単です。

### 2.6 純粋な状態機械（`src/game-logic.ts`）

- ゲーム進行を I/O から切り離し、`reduce(state, event) -> {state, effects, notices}` として実装しました。
- 時刻 `now` はイベントとして注入されるので、**20秒・10秒・3.5秒の挙動を待ち時間ゼロで単体テスト**できます。
- Durable Object 側は effects（保存・配信・アラーム設定）を実行するだけの薄い層です。

## 3. 選ばなかった案と、その理由

| 案 | 採用しなかった理由 |
| --- | --- |
| **KV に状態を置く** | 結果整合（書き込みが即座に全員へ見えない）ため、同時押しの順序を保証できません。双方向プッシュもできません。 |
| **D1（SQLite）に状態を置く** | 永続化はできますが、リアルタイム配信と単一権威の仕組みがありません。早押しの勝者を1人に確定するには結局トランザクション＋通知が必要で、構成が複雑になります。点数表・問題バンクの保存には有用ですが、今回は10問をコードに内蔵するため不要でした。 |
| **Worker だけで完結（グローバル変数）** | Worker のグローバル変数はリクエスト間・インスタンス間で共有されません。部屋の状態を保持できません。 |
| **HTTP ポーリングで状態を取得** | 0.5秒間隔でも「同時押し」の公平性が崩れ（ポーリング周期で勝者が決まる）、無駄なリクエストが増えます。要件5に反します。 |
| **WebRTC / P2P で直接通信** | 参加者のブラウザ同士で勝者を決めると「サーバーが決める」という決定済み事項に反します。NAT 越えや人数分の接続網もローカル開発では過剰です。 |
| **Workers + Cloudflare Vite プラグイン** | 同じく公式のローカル実行ですが、ビルド設定が増えるだけなので、追加依存のない `wrangler dev` を選びました。 |
| **フロントエンドフレームワーク（React/Vue 等）+ バンドラ** | 画面数が4つで状態は1本のスナップショットなので、依存ゼロの DOM 描画（`public/app.js`）で十分です。依存を増やすとオフライン環境での再現性が落ちます。 |
| **回答の正誤をクライアントで判定** | 不正が可能になるため不採用（決定済み事項）。正解インデックスは「正解発表」のスナップショットでのみブラウザへ送ります。 |
| **部屋コードを UUID にする** | 人が読み上げて入力するため、紛らわしい文字（O/0/I/1）を除いた4文字コードにしました。衝突時は採番し直します。 |

## 4. プロトコル

### 4.1 HTTP

| メソッド | パス | 内容 |
| --- | --- | --- |
| POST | `/api/rooms` | 部屋コードを採番して RoomDO を初期化。`{name}` → `{code, playerId, token}` |
| POST | `/api/rooms/:code/join` | 新規参加（`{name}`）または復帰（`{name, playerId, token}`） |
| GET | `/api/rooms/:code/ws?playerId=&token=` | WebSocket へ昇格。トークン不一致は 401 |
| GET | `/api/rooms/:code/snapshot` | 現在のスナップショット（デバッグ用） |
| GET | `/api/health` | ヘルスチェック |

参加は「定員4人」「ゲーム中は新規参加不可」「復帰は定員に関係なく許可」を RoomDO が判定します。

### 4.2 WebSocket

クライアント → サーバー:

```
{t:"start"}                      ゲーム開始（ホストのみ）
{t:"buzz"}                       早押し（到着順にサーバーが判定）
{t:"answer", choice: 0..3}       回答（回答権を持つ本人のみ）
{t:"sync"}                       スナップショット要求（接続直後・取りこぼし検知時）
{t:"kick", playerId}             ロビーで切断中のプレイヤーを外す（ホストのみ）
{t:"leave"}                      退出
```

サーバー → クライアント:

```
{t:"state", ...}   部屋の全状態（全員へ同じ内容）
{t:"notice", ...}  その操作が受け付けられなかった理由（押せない等）
```

`state` の主な内容: `phase` / `players[{id,name,score,connected,lockedOut,solved}]` /
`question{index,total,text,choices}` / `questionStartedAt` / `buzzDeadline` / `answeringPlayerId` /
`answerDeadline` / `revealedIndex` / `lastAnswer` / `ranking` / `now` / `limits`。
**`correct`（正解）は `revealedIndex`（＝正解発表フェーズ）以外では送信されません。**

## 5. ゲーム進行の状態機械

```
lobby ──start(ホスト, 2〜4人)──▶ question
                                  │  buzz（最初の1人だけ通る）
                                  ▼
                              answering ──answer(正解)────────────▶ reveal
                                  │  answer(不正解)
                                  │    ├─ まだ押せる人がいる & 20秒以内 → question（再開）
                                  │    └─ 全員押せない or 20秒経過      → reveal
                                  │  10秒経過（未回答）                 → reveal
question ──20秒経過────────────────────────────────────────────────▶ reveal
reveal ──3.5秒──▶ question（次の問題）／10問終了なら finished
finished ──reset(ホスト)──▶ lobby（点数リセット）
```

- 得点: 正解 `+10` / 不正解 `-5`。
- 不正解者は `lockedOut`（その問題では早押し不可）、正解者は `solved`。
- 20秒は「問題が出てから」の早押し受付時間です。回答権を得たあとの10秒は要件6の保証を優先して
  独立した窓にしました（早押しが20秒ギリギリでも、回答者は必ず10秒もらえます）。
- 早押しの残り時間は、不正解で再開したときも最初の20秒から継続します（要件8）。

## 6. 復帰（要件10）の仕組み

1. サーバーはプレイヤーごとに `playerId` と `token`（UUID）を発行し、HTTP 応答で返します。
2. ブラウザは `localStorage` に保存します。
3. 再読み込み時は `POST /api/rooms/:code/join`（`playerId` + `token`）で本人確認し、同じ席・同じ点数で復帰します。
4. ソケットが切れた場合はクライアントが指数バックオフで自動再接続し、接続直後に `{t:"sync"}` で最新状態を取り直します。
5. 切断中も席と点数は保持されます（`connected=false` が他プレイヤーの画面に出ます）。
6. さらに、クライアントは「締切を過ぎたのに状態更新が届かない」ことを検知すると `sync` を投げ直します
   （1通取りこぼしても画面が固まらないための保険）。

## 7. 制約と割り切り

- 1部屋あたり最大4人・1接続/人（Hibernation API で十分な規模）。
- 部屋は削除しません（ローカル開発用のため。プロセスを止めれば `.wrangler/` の状態が消えます）。
- 「切断中の席」は自動では開放しません。ホストがロビーで「外す」を押すと開放されます。
  （自動削除にすると再読み込み復帰と競合するため）
- 認証はトークンのみで、パスワード等はありません（ローカル開発限定のため）。
