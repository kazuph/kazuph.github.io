# アーキテクチャ

## 全体像

```
ブラウザ (public/ の Vanilla JS SPA)
   │  静的ファイルは Workers Assets が配信
   │  参照: POST /api/create | /api/join (REST・短期)
   │  対戦: GET /ws?code=XXXX&token=... (WebSocket・常時)
   ▼
Worker (src/worker/index.ts)  ──  部屋の作成/参加のバリデーション・コード採番
   │  WS Upgrade をそのまま DO stub へ転送
   ▼
Durable Object "RoomDO" (src/worker/room.ts)  ──  部屋コードごとに1インスタンス (idFromName)
   ├─ ゲーム状態の唯一の編集者（正誤判定・点数・早押しの採番・タイマー）
   ├─ WebSocket Hibernation API（接続は生かしつつオブジェクトは休止可能。全員に状態を配信）
   ├─ Durable Object Storage（部屋状態の永続化 → プロセス再起動・再読み込みに耐える）
   └─ Durable Object Alarm（10秒/20秒/4秒 の全タイマーをサーバー側で管理）
```

## 構成要素と選んだ理由

### 1. Durable Object（部屋あたり1つ）+ WebSocket Hibernation

- **部屋 = 単一の直列化された権威主体（サーバー権威）**。早押しクイズの肝は「サーバーが最初に受け取った
  1人だけが回答権を得る」という競合制御。Durable Object は同一インスタンスへの処理が直列に実行されるため、
  2人が同じ瞬間に押してもメッセージ到着順に必ず 1人だけが回答権を得る。ロックやトランザクションの
  追加実装が不要で、仕様そのままのモデルをコードにできる。
- **Hibernation API** で待機中の WebSocket 接続をメモリに保持せず休止できる。クイズの合間（接続は生かしつつ
  進行はタイマー主導）という負荷特性に合い、DO あたりの接続余裕も増える。メッセージは接続ソケットの
  タグ（プレイヤートークン）で本人判定する。
- 部屋コードを `idFromName(code)` とすることで「コード → DO」のルーティングに KV や索引が不要。

### 2. 状態スナップショットの全量ブロードキャスト

サーバーは状態が変わるたびに **フルスナップショット（phase・問題・得点・締切・プレイヤー一覧）** を全員に配る。

- クライアントは描画だけを行い、判断・計算・申告は一切しない（正誤判定・点数・早押しの順番はすべてサーバー側で確定）。
- 全員の画面が必ず同じ情報になる（点数・残り時間・誰が回答中かがそろう）。
- 残り時間の描画用に `serverTime` も同時に配り、クライアントは `deadline - (now + clockOffset)` で
  端末時計のずれを補正する。

### 3. タイマーは Durable Object Alarm

- Hibernation API では DO は寝ていることがあるため `setTimeout` は使えない。
- 「回答締切10秒」「問題締切20秒」「正解表示4秒」「ホスト退室後の主催権限譲渡15秒」をすべて Alarm で管理し、
  次に来る締切だけを `storage.setAlarm` する。Alarm は永続化されるため wrangler dev の再起動後も正しく発火する。
- 締切超過時の処理（失答=-5点、問題締切=正解表示へ）も DO 内で完結し、ブラウザが送ってくる内容の申告は信用しない。

### 4. 永続化（Durable Object Storage）

状態を変更するたびに `storage.put("room", snapshot)` で保存する。

- ブラウザ再読み込み → 同じトークンで再接続 → 保存済みの点数・進行状態で復帰（遊び方10）。
- wrangler dev のホットリロードやクラッシュ後も部屋が消えない。

### 5. プレイヤー識別（トークン）

- 作成/参加時にサーバー側で発行する `token`（UUID）と表示用の `playerId`（p1〜p4）を分離する。
  - token は GET /ws での本人確認だけに使い、他プレイヤー向けのスナップショットには playerId のみを載せる。
  - 再接続の鍵はブラウザの localStorage に保存（`buzzool_session_v1`）。

### 6. 静的配信（Workers Assets）

クライアントはビルド不要の Vanilla JS（public/）。`assets.directory` を設定すると静的ファイルは Assets が
直配信し、API・WS だけ Worker の fetch に流れる。ビルドパイプラインがなく依存が最小。
UI の状態遷移は「サーバーから届いたスナップショットを描画する」だけなので、フレームワークなしでも複雑化しない。

### 7. 内蔵問題（10問・4択・日本語）

外部APIを使わず `src/shared/questions.ts` に10問を内蔵（外部API呼び出しコードは存在しない）。
正解位置は各問でばらしている。出題順は DO が Fisher-Yates（`crypto.getRandomValues`）でシャッフルする。

## 採用しなかった案と理由

| 案 | 不採用の理由 |
| --- | --- |
| REST ポーリングのみでリアルタイム化しない | 「早押し」は数百ミリ秒の競合が本質。ポーリングだと公平性・視認性・負荷のいずれかが妥協になる。WebSocket + Hibernation なら Cloudflare の機能内で足りる |
| D1 / KV に部屋状態を保存 | 部屋1つ（最大4人・10問）のようなホットな状態には向かない。書き込み頻度が高く整合性の管理が増える。DO Storage は原子性・直列性が保証され「部屋ごとの局所状態」にまさに合致 |
| 1 DO に全部屋を集約（シャード） | 直列化の単位が全体になり部屋をまたぐ干渉・レイテンシが増える。部屋ごとに独立させる方が分かりやすくスケールする |
| ゲームロジックをクライアントに置く（サーバーは中継のみ） | 決定済み事項「正誤判定・点数・早押しの順番はサーバー側」に違反。ブラウザ側は改竄が容易 |
| ブラウザの申告で回答権などの判定 | 同上。本人確認は必ずサーバー保存のトークンで行う |
| 有料・外部のリアルタイム配信サービス / ミドルウェア | 決定済み事項（有料・外部サービス不使用）。Workers + DO の WebSocket で完結する |
| React / Vue 等のフレームワーク+ビルド | 状態は「スナップショットを描画する」だけなので Vanilla JS で十分。ビルドパイプラインをなくすことで `npm run dev` だけで完結する手軽さを優先 |

## テストのアーキテクチャ

| レイヤ | 対象 | 実行 |
| --- | --- | --- |
| 結合テスト | RoomDO と Worker を本物の workerd で動かす。同時押しの1人制限、採点、タイムアウト、再接続、満員、開始制限、4人同時フルゲーム | `npm test`（@cloudflare/vitest-pool-workers） |
| ブラウザE2E | 実ブラウザ × wrangler dev で4人同時対戦、5人目の拒否と理由表示、再読み込み復帰 | `npm run test:e2e`（Playwright） |
| スクリーンショット | ロビー・出題中・回答中・結果 × PC/スマホ幅 | `npm run shots` → `.artifacts/` |

同時押しや「誰も押さないと進むか」など実時間の待ちが必要な確認は、ロジックは完全に同じで待ち時間だけ短い
`fast` モード（部屋作成時のオプション）で行う。普通に遊ぶときの 10秒/20秒/4秒は
`src/shared/types.ts` の定数がそのまま使われる。
