# アーキテクチャ

## 採用した構成

Cloudflare Workers が HTTP と静的ファイルを配信し、部屋ごとに1つの SQLite-backed Durable Object がゲームを管理します。Durable Object Storage に状態全体を保存し、同じオブジェクトで早押しを順番に処理するため、同時押しでもサーバーが最初に受け取った1人だけに回答権を渡せます。

Durable Object は WebSocket Hibernation API で接続を受け付け、参加者ごとに状態全量を配信します。次の締め切り1つだけを Alarm に予約します。アプリ本体は `public/` の HTML・CSS・JavaScript で、フロントエンドのビルド工程はありません。

## 部屋と通信

- 部屋コードは紛らわしい `0/O` と `1/I` を使わない6文字です。コードから `ROOM.idFromName(code)` で Durable Object を取得します。
- `POST /api/rooms` が部屋とホストを作成します。
- `POST /api/rooms/:code/join` が参加者を登録し、4人を超える参加と開始後の参加を拒否します。
- `GET /api/rooms/:code/ws?token=…` は参加 token を確認して WebSocket に切り替えます。
- クライアントは `start`、`buzz`、`answer` を送ります。サーバーは全量の `state` を返し、入力検証に失敗した操作は `error` を返します。

参加 token はブラウザーの localStorage と Durable Object 内に保存し、状態配信には含めません。ゲーム中の正解番号は、正解表示フェーズになるまで配信しません。

## ゲーム規則

`src/game.ts` は時間を引数として受け取る純粋関数です。各メッセージや Alarm の処理前に `tick(state, now)` を適用し、期限切れを入力より先に反映します。早押し・回答・採点・失格・正解表示・順位計算をここで行います。問題は `src/questions.ts` の12問からサーバーが10問を選びます。

1問の20秒期限と回答者の10秒期限のうち、早いほうを締め切りに使います。正解後、または全員が不正解・時間切れになった後は3秒の正解表示を経て次へ進みます。同点は同じ順位です。

## 再接続と参加者表示

接続が切れても参加者レコードと得点は削除しません。新しい WebSocket が同じ token で接続すると、同じプレイヤーの古いソケットを閉じます。画面は1秒後から再接続し、オンライン復帰時は直ちに再接続します。接続状態もゲーム状態として全員に配信します。

## 代替案

- **D1 / KV:** 部屋内の点数・回答権・期限を複数サービスに分ける必要がなく、早押しの順序と状態更新を1か所で確定できる Durable Objects を選びました。D1 や KV は別部屋を横断するデータが不要な今回のゲームでは追加の整合性境界になります。
- **外部リアルタイムサービス:** ローカル限定・有料サービス不使用の決定に合わないため採用していません。
- **フロントエンドフレームワーク:** 4画面の操作に必要な状態は小さく、PLAN.md のビルドなし HTML/CSS/JavaScript 構成に合わせました。
