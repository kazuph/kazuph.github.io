# アーキテクチャ

## 全体像

```
ブラウザ(4人)
   │  POST /api/rooms, /api/rooms/:code/join   … 部屋の作成・参加
   │  WebSocket /api/rooms/:code/ws?token=…    … 状態の受け取りと操作の送信
   ▼
Workers (src/worker.ts)          … /api/* の入口。URL から部屋コードを取り出す
   ▼
Durable Object "Room" (src/room.ts)  … 1部屋 = 1オブジェクト
   ├─ storage (SQLite)   … ゲーム状態の保存
   ├─ WebSocket 群        … 全員への状態配信（Hibernation API）
   └─ Alarm               … 締め切り時刻になったら tick を進める
```

- 実行環境は Cloudflare Workers のランタイム。ローカルは `wrangler dev` だけ。
- フロントはビルドなしの素の HTML/CSS/JavaScript（`public/`）。静的配信は Workers Static Assets。
- 依存は devDependencies の `wrangler` / `typescript` / `@cloudflare/workers-types` / `vitest` / `@playwright/test` のみ。

## なぜこの構成か

### 1部屋 = 1 Durable Object

早押しは「最初に受け取った1人だけが回答権を得る」という**競合の解決**が本質です。
複数の Worker インスタンスや複数プロセスで同じ部屋を扱うと、到着順の判定がぶれます。
Durable Object は同じ部屋への入力を1か所（1つのシングルトンな実行主体）に集約するので、
「サーバーが最初に受け取った順」をそのまま唯一の順序として扱えます。これが最大の理由です。

- 部屋コードから `env.ROOM.idFromName(code)` で引くので、URL が部屋の識別子になります。
- 1部屋の人数は4人なので、1オブジェクトが持つ状態も小さく、1つの JSON として保存できます。

### Durable Objects の SQLite 版

`migrations` の `new_sqlite_classes` を使い、SQLite ベースの Durable Object にしています。
新規作成時点で推奨される保存方式で、`ctx.storage.put/get` で状態（1つの JSON）をそのまま保存できます。
複雑なクエリは不要なので SQL を直接は使わず、KV 風の `put/get` にしています。

### WebSocket（Hibernation API）

状態は毎回**全量**を送ります。4人・10問の問題では状態が小さく、差分を組み立てるより
「全量を送って、クライアントはそれを描画するだけ」のほうが事故が少ないためです。

`ctx.acceptWebSocket()` を使う Hibernation 対応の WebSocket にしているので、
誰も操作していない時間は Durable Object が休めます。Alarm で締め切りにだけ起きて処理します。

- 接続は `token`（プレイヤーごとの乱数）で認証します。token を知らない他人には成りすませません。
- 同じ token の新しい接続が来たら古い接続を閉じ、席と点数はそのまま引き継ぎます（再接続）。
- 正解の番号は `reveal` のときだけ送ります。出題中・回答中の状態には正解を含めません。

### Alarm で締め切りを進める

20秒（問題）・10秒（回答）・3秒（正解表示）の締め切りは、Alarm を「次に必要ないちばん近い締め切り」1つだけ予約して処理します。
メッセージを受けたときも Alarm のときも、まず締め切りを過ぎた処理を `tick()` で進めてから入力を処理します。
これで、誰も操作しなくてもサーバーの時計だけで進行します。時刻はすべてサーバーの `Date.now()` で決めます。

### 判定は純粋関数に集約

`src/game.ts` は時刻 `now` を引数で受け取る純粋関数だけにしてあります。
正誤・点数・早押しの順番・失格・reveal への遷移はすべてここで決まり、
Durable Object は「呼ぶ・保存する・配る」だけです。
おかげで「4人の押す順24通りで回答権が1人だけ」といった競合を、実サーバーなしの高速な単体テストで網羅できます。

## 選ばなかった案

| 案 | 却下した理由 |
|---|---|
| KV / Cache API に状態を保存 | 書き込みの反映が遅く、順序も保証されない。早押しの同時到着を裁けない |
| D1（SQL）に状態を保存 | 早押しの到着順を一意に決めるには結局どこかで直列化が必要。1部屋の小さな状態に対して大げさ |
| 全部 HTTP のポーリング | 早押しの順番が端末のタイミング任せになり「サーバーが最初に受け取った1人」を保証しづらい。残り時間も滑らかに出せない |
| 外部のリアルタイム配信サービス（Pusher 等） | 有料の外部サービスは使わない方針。Cloudflare 内で完結させる |
| Room を PartyKit / フレームワークで作る | 依存を増やさず、Durable Object を直接使えば十分。ビルド工程も持たないほうが読みやすい |
| 状態を差分で配信 | 実装ミスで全員の画面がずれる危険がある。全量配信のほうが確実 |

## 時計の扱い

各 state メッセージに `serverNow`（サーバーの現在時刻）を入れます。
ブラウザは「serverNow − 自分の時計」の差を覚えておき、残り時間はその補正値で計算します。
端末の時計がずれていても、全員が同じ残り時間を見られます。

## エラー時の考え方

- 定員オーバー、開始後の参加、token 不一致などの理由は HTTP のステータスと `{ error }` で返し、画面に出す。
- 不正な `buzz` / `answer`（順番違い・回答権なし）はその人にだけ `{ t: "error", message }` を返す。
- 保存したセッション（部屋コード・token）で一度も状態を受け取れないまま何度も再接続に失敗したら、古いセッションとみなして消し、入口画面に戻して理由を表示する（サーバーを再起動した後など）。
- 勝敗・点数はサーバーが決めるので、ブラウザからの申告は一切信用しません。
