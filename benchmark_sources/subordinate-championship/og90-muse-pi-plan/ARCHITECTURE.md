# アーキテクチャ

## 採用した構成

**Cloudflare Workers + Durable Objects（SQLite 版）+ WebSocket Hibernation API + Alarm + Workers Static Assets。1部屋 = 1つの Durable Object。**

- 部屋コードから `env.ROOM.idFromName(code)` で Durable Object を引く。同じ部屋の全員が同じオブジェクトに集まるため、早押しの先着判定・点数・フェーズ遷移を単一の場所で直列に処理でき、競合が起きない。
- ブラウザと Durable Object の間は WebSocket（Hibernation API）でつなぎ、状態が変わるたびに全量の `state` を全員へ配信する。残り時間は `serverNow` との差分で各端末が描画するため、端末時計のずれに左右されない。
- 締め切り（問題20秒・回答10秒・正解表示3秒）は Alarm で管理し、「いちばん近い締め切り」1つだけを予約する。Alarm が鳴るたびに `tick` で期限切れをまとめて進め、再配信・再予約する。
- ルーム状態は Durable Object 内蔵の SQLite に JSON で保存する。Hibernation 中の再起動やAlarm 起動時にも席・点数が残る。
- フロントはビルドなしの素の HTML / CSS / JS（`public/`、Workers Static Assets で配信）。正誤判定・点数・早押し順はサーバー（`src/game.ts` の純粋関数＋ `src/room.ts`）が決め、ブラウザは表示と入力送信だけを行う。出題中の配信には正解番号も他人 token も含めない。
- 切断検知はクライアントの5秒ごとのハートビート（`ping`）と、サーバーの12秒タイムアウトの組み合わせで行う。TCP の切断検出を待たず、オフライン継続でも12秒程度で「接続が切れています」と表示できる。再接続時は保存した token で同一プレイヤーとして復帰し、古い接続は新しい接続が置き換える。

## 選ばなかった案と理由

| 案 | 不採用の理由 |
|---|---|
| Workers のみ＋定期ポーリング（WebSocket なし） | 早押しの同時性をポーリング間隔でしか保証できず、「サーバーが最初に受け取った1人だけ」の判定が曖昧になる。無駄なリクエストも増える |
| D1 / KV に状態を置く | 部屋ごとの直列化が自前で必要になり、同時押しの原子性（最初の1人だけ）を保つ実装が複雑になる。DO なら1オブジェクト＝1部屋で自然に直列化できる |
| 外部のリアルタイム配信サービス（Pusher・Ably・Socket.IO サーバー等） | 課題の決定事項で禁止（Cloudflare の中で完結・有料外部サービスなし）。DO の WebSocket で十分足りる |
| フロントのフレームワーク（React・Vite 等） | ビルド工程と依存が増えるだけで、この規模の画面遷移・描画には素の JS で足りる。PLAN の指定どおり素の HTML/CSS/JS にした |
| Durable Objects の旧来ストレージ（KV API） | SQLite 版のほうがクエリが素直で、将来の拡張（履歴・ランキング保存）にも向く。新規作成なので移行コストもない |

## テスト方針

- 規則の分岐（早押し順列・点数・締め切り・秘匿）は副作用のない `game.ts` に集め、vitest の単体テストで網羅する。特に「4人の `buzz` を24通り全部の順番で処理しても回答権は最初の1人だけ」を機械的に確かめる。
- 実ブラウザの結合（Playwright、`wrangler dev` を `webServer` で起動）では時間を縮めず、同時押し・再読み込み・オフライン・20秒/10秒の実時間締め切り・4画面の同期・10問完走を確かめる。タイマー系の不安定さを避けるため、待機はすべて表示内容のポーリングで行う。
